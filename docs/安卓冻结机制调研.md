# 安卓「冻结（App Freezer）」机制调研

调研日期：2026-10-23
场景：zmd-charge 前台服务 + 动态 ACTION_POWER_CONNECTED 广播触发插电弹岛，在 iQOO V2403A（OriginOS 6 / Android 16）上静置后被冻结，广播收不到。

## 一、AOSP 的 cached_apps_freezer（Android 12+）
- 系统把「缓存」态进程 SIGSTOP 挂起（不是 kill），`dumpsys jobscheduler` 里显示 frozen package。
- 豁免：active/前台 standby bucket、有前台服务/前台 Job/系统绑定等。
- 它是独立于 standby-bucket / Doze / appops 的一层，所以 `set-standby-bucket active`、`appops RUN_ANY_IN_BACKGROUND allow` 都解不开。
- 资料：https://source.android.com/docs/core/perf/cached-apps-freezer

## 二、vivo/OriginOS 私有后台高耗电管理
- vivo 私有「后台高耗电管理」（com.iqoo.powersaving BackgroundHighUsageActivity / ExcessivePowerManagerActivity），把长期后台 app 标为高耗电并限/冻。
- 白名单 = 「设置→电池→后台高耗电管理→把 app 设为允许/不限制」+「自启动」白名单。
- **vivo 冻结不看 FGS 状态**，私有冻结名单可覆盖前台进程，独立于 AOSP bucket/appops —— 这就是解不开的根因（推断，依据实测）。
- vivo 官方说明：https://www.vivo.com/en/support/questionByTitle?title=How%20to%20turn%20on/off%20High%20background%20power%20consumption?

## 三、国产 ROM 普遍机制
- 小米/华为/OPPO/vivo/荣耀都有类似冻结+白名单，普遍需要「自启动 + 后台高耗电豁免 + 忽略电池优化」三件套手动设置。
- 汇总路径：https://dontkillmyapp.com/vivo ；原理：https://blog.csdn.net/weixin_34343308/article/details/91562211

## 四、Android 13+ FGS / 隐式广播
- AOSP 前台服务通常豁免普通缓存冻结，但 Android 14/15 收紧 FGS 启动限制；且厂商私有冻结可覆盖 FGS。
- ACTION_POWER_CONNECTED 属隐式广播，自 Android 8 后台限制后不可靠，官方建议迁移 JobScheduler：https://developer.android.com/about/versions/oreo/background

## 五、务实方案（开源、无 root）
1. **用户手动加白名单（唯一根治，可靠性最高）**：vivo「后台高耗电→允许」+「自启动」+ 忽略电池优化。
2. 保留前台服务（已有，解不了私有冻结）。
3. 兜底：WorkManager/JobScheduler 替代隐式广播。
4. `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 弹框引导（AOSP 层，不等于解冻结名单）。
5. 无通用厂商保活 SDK（非厂商合作不可用）。

**根因一句话**：App 没进 vivo 私有「后台高耗电→允许」名单，跟前台服务无关。

## 六、躲过冻结：三层兜底（v1.0.7 落地实现）

> 前提：无 root、无 Xposed、不要求用户手动改系统设置。目标是「有动画」，不是「每台都保证准时」。

**结论先行**：没有任何代码能做到 100% 在冻结下准时收广播。能做的只有三件事——减小被冻结窗口、多处埋兜底唤醒、利用系统托管的通道。

### 层 1：JobScheduler(setRequiresCharging) —— 唯一不怕冻结的唤醒通道（P0）

- 任务由 system_server 的 JobSchedulerService 调度，**充电约束满足时会拉起进程**，不需要进程预先活着。
- 这是插电瞬间把进程从冻结态捞起来的唯一正路；厂商可能延迟数秒到数十秒，但总好过完全收不到。
- 关键区分：**cached-app-freezer 是 SIGSTOP（任务仍存，解冻可续）**，不是 force-stop。真 force-stop 会清掉 Job/广播/闹钟，那种情况应用代码无解。
- 实现：`ChargeTriggerJobService` + `Keepalive.scheduleChargeJob()`，onStartJob 里统一走 `Keepalive.rearm()`。

### 层 2：动态 ACTION_POWER_CONNECTED —— 进程活着时的秒级响应

- O+ 起该广播不在隐式广播豁免清单，只能运行时动态注册；前提是进程没被冻死。
- 它救不了冻结，但**是解冻自愈后第一条该重新武装的路**，也是未冻结时最快的一条。
- 实现：`Keepalive.registerPower()`，幂等（已注册则跳过）。

### 层 3：rearm() 全入口自愈（幂等）

挂到所有能把进程拉活的入口，任一入口进来都重新武装：

- 开 App（`App.onCreate`）
- 开机（`BootReceiver`）
- 点组件 / 组件被添加（`BatteryWidgetProvider.onUpdate / onEnabled`）
- 充电 Job 触发（`ChargeTriggerJobService.onStartJob`）
- 前台服务启动（`LiveService.onCreate / onStartCommand`）

rearm 做且只做三件事：重注册插拔电广播、重排充电 Job、若当前正在充电则直接补一次弹岛（解冻后不必等下一次插拔）。

### FGS 怎么摆

- **FGS 不是防冻结令牌**，长期常驻 FGS 在国产 ROM 上反而容易成为清理目标。
- Android 15 起 FGS 有硬超时（shortService 3 分钟），播个动画绰绰有余。
- 策略：弹岛不再依赖 FGS 常驻——广播由 Keepalive 在进程存活时注册，进程死了靠充电 Job 拉起。FGS 保留给「实时刷新」这个用户可选功能。

### 小组件自愈的边界

- onUpdate 回调在 provider 进程执行，进程被冻则不跑；**用户点组件 → 拉活进程 → rearm** 是有效自愈入口。
- Android 15 起 force-stop 会连带禁用桌面小组件（需用户重加），这条路在 force-stop 语义下也断。

## 七、实测侦查命令（adb，开发期用）

- `adb shell dumpsys jobscheduler | grep -i com.zmd.charge` —— 看是否 frozen / pending / active。
- `adb shell dumpsys deviceidle` —— 看 Doze 状态。
- `adb shell dumpsys activity processes | grep -i zmd` —— 看进程状态（cached / frozen）。
- 已排除的无效手段：`am set-standby-bucket active`、`appops RUN_ANY_IN_BACKGROUND allow`（vivo 私有冻结层独立于此）。

## 八、用户侧唯一根治手段

不开系统开关时，代码极限是「JobScheduler 兜底 + 有延迟的动画」。要接近准时，用户仍需三件套：

1. **自启动**：设置 → 更多设置 → 应用 → 自启动 → 打开本应用。
2. **电池无限制**：应用详情 → 电池 → 后台耗电管理 → 无限制。
3. **后台高耗电管理 → 允许**：设置 → 电池 → 后台高耗电管理 → 本应用设为允许/不限制。

资料：https://dontkillmyapp.com/vivo

## 九、v1.0.7 实测结论（2026-10-23，iQOO V2403A / OriginOS 6 / Android 16）

在真机上做了三轮对照实验，推翻了上文「JobScheduler 能绕过冻结」的推断：

### 9.1 冻结确实存在，且是 AOSP cached_apps_freezer 表现

```
adb shell dumpsys jobscheduler | grep "frozen package name"
frozen package name: {... Pair{com.zmd.charge 10457} ...}
```

同时广播队列里能看到：

```
BroadcastProcessQueue{... 11342:com.zmd.charge/u0a457} not runnable because INFINITE_DEFER
    state:FRZ|FROZEN
    ACTION_POWER_CONNECTED ... DEFERRED for registered BroadcastFilter{... com.zmd.charge ...}
```

**插电广播被 DEFERRED 挂起，这就是「插电不弹岛」的直接原因。**

### 9.2 冻结状态下，JobScheduler 也被拦（关键负结果）

- 冻结中执行 `cmd jobscheduler run -f com.zmd.charge 1002`，系统回 `Running job [FORCED]`，
  **但进程日志一条都没有**，job 执行记录里也没有 START-P。
- 说明 vivo 的冻结层不只挂起广播投递，**连 JobScheduler 的调度执行都被一起冻结**。
- 这推翻了「JobScheduler 是唯一不怕冻结的通道」的推断 —— 至少在 OriginOS 6 上不成立。

### 9.3 解冻后一切正常（对照实验）

- 冻结中执行 `cmd jobscheduler run -f`：无日志、无执行。
- 用户点开 App（或系统主动解冻）后，同一命令：立刻打印
  `Job: 充电任务触发（system_server 拉起进程）`，组件正常刷新。
- 同样地，打开 App 后 `frozen package name` 列表里 zmd 立即消失。

### 9.4 修正后的现实结论

| 手段 | 冻结中 | 解冻后 |
|---|---|---|
| 动态 ACTION_POWER_CONNECTED | 被 DEFERRED，收不到 | 正常 |
| JobScheduler 充电任务 | 强制也跑不起来 | 正常 |
| 前台服务 | 保不住（进程被冻） | — |
| 用户点开 App / 点组件 | 立即解冻，恢复一切 | — |

**唯一能真正解决冻结的还是系统白名单（后台高耗电→允许 + 自启动）。**
JobScheduler 的价值降级为：在「未被冻结」的常态下提供兜底，以及在被解冻的瞬间立刻恢复武装。

### 9.5 v1.0.7 实际落地的代码

即便 JobScheduler 在冻结中无效，下列改动仍然带来实际收益（都在解冻后/未冻结时生效）：

1. `Keepalive.rearm()`：统一武装插拔电广播 + 重排 Job + 若在充电则补弹岛，挂在 App.onCreate / BootReceiver / 组件 onUpdate / onEnabled / LiveService / Job onStart 六个入口，幂等。
2. `Keepalive.onWakeFromJob()`：Job 唤醒时只做「武装 + 补播」，**不重排 Job**（否则充电约束满足时会立刻再触发，形成 hot loop，实测每秒数次）。
3. 补播闸门 `markRearmPopupOnce()`：进程重启时多个入口并发调 rearm 会连弹多次（实测 8 次），用进程级一次性闸限成 1 次；真插电 `onChargeConnected` 会先占闸，避免随后 rearm/Job 重复补播。
4. `ChargePop.show/launch` 加 `@Synchronized`：冷却检查与时间戳更新原子化，堵住并发穿透。
