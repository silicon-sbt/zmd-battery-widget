# 做成「岛」可行吗？—— 调研与建议

> 调研日期：2026-03 ｜ 对象：zmd-charge（终末地电力 HUD 电量组件）
> 结论先行：**能做，但只能做「充电时上岛」这一刀，不建议做常驻自绘岛。**

---

## 0. 先分清：评论区想要的「岛」其实是两种东西

| | A. 上系统岛 | B. 自绘悬浮岛 |
|---|---|---|
| 做法 | 发一条 Android 16 **Live Update**（实时更新）通知，交给系统/厂商渲染成状态栏芯片、锁屏卡片、原子岛/流体云/灵动胶囊 | 自己画一个悬浮窗，贴在挖孔/状态栏旁边，模仿 iPhone 灵动岛 |
| 长相 | **系统说了算**（终末地的美术上不去） | 100% 自己画，能完全复刻终末地 HUD |
| 权限 | 只要一个普通权限，无弹窗 | 悬浮窗 或 无障碍，+ 常驻前台服务通知 |
| 耗电 | ≈0（系统托管的通知） | 常驻前台服务 + 过度绘制，实打实耗电 |
| 覆盖设备 | Android 16+（且看厂商是否接管） | 任意 Android（含老机型） |
| 锁屏可见 | ✅ 锁屏会展开（系统行为） | ❌ 悬浮窗基本进不了锁屏 |
| 风险 | 官方使用准则限制用途 | Android 17 起收紧无障碍；观感与真岛打架；用户反感 |

**关键点：A 和 B 的观感完全相反。** A 最省事但"丑不丑不由你"；B 你能画终末地，但要背权限、耗电和"和厂商真岛撞车"的锅。

---

## 1. 路线 A：官方"上岛"通道（Android 16 Live Updates）

### 1.1 成为实时更新的硬性条件（官方原文，全部满足才行）

- 必须是标准样式：`BigTextStyle` / `CallStyle` / `ProgressStyle` / `MetricStyle`
- manifest 声明 **非运行时**权限 `android.permission.POST_PROMOTED_NOTIFICATIONS`
- 请求提升：`Notification.Builder#setRequestPromotedOngoing(true)`
- 必须 `setOngoing(true)`
- 必须有 `contentTitle`
- **禁止 `customContentView`（禁止 RemoteViews）** ← 终末地美术的死刑判决
- 不能是分组摘要，不能 `setColorized(true)`，渠道重要性不能是 `IMPORTANCE_MIN`

判定 API：`Notification.FLAG_PROMOTED_ONGOING` / `Notification.hasPromotableCharacteristics()` / `NotificationManager.canPostPromotedNotifications()`；引导页跳 `Settings.ACTION_MANAGE_APP_PROMOTED_NOTIFICATIONS`。

### 1.2 使用准则（这是"搞头"的真正天花板）

用于**进行中（ongoing）、用户主动发起（user-initiated）、时间敏感（time-sensitive）**的活动：

- **恰当用途**：导航中、通话中、打车/外卖进行中
- **明确不当用途**：广告、推广、聊天消息、提醒、未来日程、**以及"应用功能的快捷入口"**（官方原话：想要这个请用 app widget 或 QS 磁贴）
- **禁止环境性信息（ambient information）**：官方原话 "Don't show ambient information, such as that about the user's environment"

👉 推导：
- **"平时常驻显示电量"= ambient，属于官方点名的不当用途。** 做了可能被系统降级，或用户直接关掉本应用的实时更新权限（官方明确写了 "Posting unwanted Live Updates might cause users to revoke an app's posting permission"）。
- **"充电中 0→100%"** 才是站得住的：用户插电发起、有明确起止、有等待完成的诉求（时间敏感）。这是唯一值得做的形态。

### 1.3 状态栏芯片的物理限制

- 芯片最大 **96dp**，含图标 + 可选文字
- 文字 <7 字符才完整显示；显示不足一半就只剩图标
- 文案控制在 3~6 个字（"充电中" / "78%" / "12 分钟"）

## 2. 各家厂商对 Live Updates 的兼容现状（2026-03）

| 厂商/系统 | 状态 | 依据 |
|---|---|---|
| Pixel / AOSP | ✅ 原生（状态栏芯片 + 锁屏展开） | Android 16/17 官方文档与示例 |
| OPPO ColorOS 16 | ✅ **官方开放路线**，完整接入原生 Live Updates API，"双兼容方案"，遵循 Google 规范即可直接适配 | ColorOS 设计总监陈希公开表态（IT之家） |
| 三星 One UI 8 | ✅ 任何应用都能进 Now Bar | Android Authority 报道 |
| 小米 澎湃 OS 3 超级岛 | ⚠️ 有官方接入指南（`miui.focus.param`），但**要注册小米开发者、上架应用、场景预审、设备白名单、正式包审核、灰度 7~15 天**；社区反馈其亦已支持原生 Live Updates（弱证据） | 小米开放平台文档 + IT之家 |
| 荣耀 MagicOS | ⏳ 官方产品经理 2026-03 回复"在做的"；当前还在等 | 荣耀俱乐部官方回复 |
| **vivo OriginOS 6** | ❓ **无公开文档**。原子岛/原子通知目前是**合作制**（高德驾车导航、京东外卖、钉钉来电、微信/支付宝…） | IT之家多条"上岛"新闻均为一对一合作 |

**对您这台 vivo 的意义**：ColorOS/Pixel/三星已证明"第三方自上线岛"这条路走得通（开源项目 FluidCapsule 就是靠标准实时通知在 ColorOS 与 Pixel 上跑通的，不需要 root、不需要白名单）；**vivo 是唯一未知项**，且恰好是您自己的机器。

## 3. 路线 B：自绘悬浮岛（dynamicSpot 模式）的真实代价

两种宿主：
1. **SYSTEM_ALERT_WINDOW 悬浮窗**（`TYPE_APPLICATION_OVERLAY`）：只需"显示在其他应用上层"权限，最轻。前例：Overlay Battery Bar（Play 在架多年的纯悬浮窗电池条）。
2. **无障碍悬浮层**（`TYPE_ACCESSIBILITY_OVERLAY`）：不用悬浮窗权限、不用常驻通知，但要求无障碍服务。前例：dynamicSpot。

代价清单（按重要性）：

- **权限与合规**：Android 17 的**高级保护模式**已把"非无障碍类应用"调用 AccessibilityService 直接封死，dynamicSpot 被点名举例 → 无障碍路线的长期寿命有问题；悬浮窗路线虽然更稳，但国产 ROM 还要过"后台弹窗"等额外开关。
- **常驻成本**：要一直显示就得常驻前台服务 + 一条消不掉的通知，再加持续绘制 → 耗电与内存都不好看。
- **锁屏依旧无解**：悬浮窗不显示在锁屏上。这条与上一轮结论一致——**岛并不能解决"锁屏看电量"**。
- **撞车**：挖孔、状态栏图标、厂商真岛（原子岛/流体云/灵动胶囊）会同时出现 → **两个岛**，这是最容易"丑"的地方。
- **观感成本极高**：要与系统动画、圆角、模糊、浅深色、横竖屏、折叠屏共存。上一轮的胶囊通知你的评语是"还是丑"，自绘岛只会更难。
- **参考项目**：MaterialYou Dynamic Island（2022 开源，已基本停更）；HyperIsland（HyperOS 超级岛增强，**需 LSPosed/root**，不是普通 App 能走的路）。

## 4. 三条路线的决策矩阵

| 方案 | 开发成本 | 观感可控 | 覆盖 | 风险 | 建议 |
|---|---|---|---|---|---|
| **A-1 充电时上岛**（Live Updates） | 1~2 天 | ❌ 系统样式 | Android 16+ | 低（合规） | ✅ **推荐** |
| A-2 常驻电量上岛 | 1 天 | ❌ | Android 16+ | 高（官方不当用途、用户可撤销） | ❌ 不做 |
| B 自绘悬浮岛 | 1~2 周 | ✅ 终末地风 | 全 Android | 高（权限/耗电/撞车/Android 17） | ❌ 不做（可留实验开关） |
| C 小米超级岛 SDK | 数周 + 审核 | 半可控 | 仅小米 | 需上架审核、灰度排队 | ❌ 不做 |

## 5. 唯一待验证的关键未知项

**vivo OriginOS 6 会不会接管标准 Android 16 实时通知？**

验证方法（约 1 小时，可完全还原）：
1. 写一个最小测试 APK：一个按钮，发一条 `ProgressStyle` + `POST_PROMOTED_NOTIFICATIONS` + `requestPromotedOngoing` 的通知；
2. 装到 V2403A 上执行，依次看三处：**状态栏有没有芯片**、**原子岛有没有接管/展开**、**锁屏是否展开**；
3. 记录结论后卸载。

这一步的结论直接决定档位 A-1 值不值得做，也决定 README / 评论区怎么回复。

## 6. 如果做 A-1，设计草案

- **触发**：`ACTION_BATTERY_CHANGED` 里 `plugged != 0 && level < 100` → 发；拔电或满电 → `cancel()`。
- **形态**：`ProgressStyle`，progress = 当前电量百分比，tracker icon 用现有矢量图标，segments/points 表示快充段与 80% 节点。
- **文案**：标题「终末地 · 充能中」，正文「78% · 预计 12 分钟后充满」，芯片短文本「78%」（<7 字符）。
- **开关**：设置页新增「充电时上岛（Android 16+）」，低版本/不支持设备 **置灰并说明原因**，不要静默失败。
- **兜底**：`canPostPromotedNotifications()` 为 false 就不发（用户可能在系统里关了）。
- **不做**：放电时常驻、电量低提醒（那是普通通知的事）。

## 7. 给评论区的一段回复模板

> 感谢建议～ 岛上这门手艺我调研过了：Android 16 起了官方的「实时更新（Live Updates）」通道，ColorOS 16、三星 One UI 8、Pixel 都是开放的，小米超级岛要开发者上架+审核，荣耀在做，vivo 还没公开接口。
> 但官方对用途有硬性规定：必须是"进行中、用户发起、时间敏感"的活动，**明确不允许把常驻环境信息（比如平时的电量）放上去**，也不许自定义外观（终末地的画风上不去）。所以计划是**充电时上岛**：插电后显示充能进度，充满自动撤掉。自绘一个常驻悬浮岛不做——要无障碍/悬浮窗权限、空耗电，还会和系统自己的岛撞在一起。
